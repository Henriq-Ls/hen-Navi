[IA-PAINEL] STATUS: RESOLVIDO
Data descoberta: 2026-11-03
Descrição: O botão/atalho de IA e ações que limpam o contexto falhavam porque
  a janela não criava self.ai_dock.
Como reproduzir: Abrir o navegador e tentar abrir Configurações de IA ou fechar
  uma aba secundária; a execução antiga podia lançar AttributeError.

  _build_interface.

  das abas e manter teste de regressão para essa inicialização.

  continua pendente porque PySide6 não está disponível no ambiente de testes.

[IA-OLLAMA] STATUS: RESOLVIDO
Data descoberta: 2026-11-03
Descrição: Um novo cadastro Ollama podia ficar sem URL base e não consultava
  automaticamente os modelos locais.
Como reproduzir: Abrir um novo cadastro de provedor e deixar Ollama selecionado;

[VIDEO-CODECS] STATUS: INVESTIGANDO
Data descoberta: 2026-11-03
Descrição: Vídeos HTML5 de vários sites não reproduzem; o QtWebEngine pode abrir
  uma página de mídia direta com controles mínimos, mas sem imagem.
Como reproduzir: Abrir um vídeo em sites que não sejam YouTube e tentar iniciar
  a reprodução.
Causa suspeita: O QtWebEngine só reproduz MP4/H.264 quando esses codecs foram
  incluídos na compilação. A configuração atual não compila nem valida o Qt.
Solução / workaround: Adicionado diagnóstico local no menu para consultar
  H.264/MP4, AAC, VP9, AV1 e MediaSource. Executar no Windows e decidir o próximo
  passo conforme o resultado; não há plugin HTML/Flash a instalar.
Verificação: Testes da função de diagnóstico passaram; reprodução real no
  Windows ainda não verificada.

[UPLOAD-SELETOR] STATUS: VALIDADO NO WINDOWS
Data descoberta: 2026-11-07
Descrição: Ao iniciar um envio em diferentes sites, o hen-Nave trava antes de
  permitir a escolha do arquivo ou da pasta.
Como reproduzir: Abrir um formulário de upload e acionar o seletor de arquivos.
Causa suspeita: O fluxo anterior delegava ao seletor nativo do QtWebEngine. O
  arquivo de diagnóstico enviado não registra uma exceção do upload; a linha
  main.py:165 aponta para o loop normal do aplicativo, e ResizeObserver é um
  aviso JavaScript da página.
Solução / workaround: Substituído o seletor nativo por QFileDialog Qt não nativo,
  modal à janela do hen-Nave, com tratamento explícito para arquivo, seleção
  múltipla e pastas. Cancelar retorna uma seleção vazia.
Verificação: Testes de integração estática e compileall passaram. O usuário
  confirmou que realizou um upload no Windows sem o travamento descrito.
Atualização: A interface agora traduz os controles do seletor, ordena os itens
  alfabeticamente e mostra atalhos para Área de Trabalho e Downloads. O log mais
  recente também contém `stat hen-Navi/.: not a directory` durante upload no
  Replit. O código do QtWebEngine cria marcadores de diretório com `/.` durante
  sua enumeração; alguns sites podem tentar tratar esses marcadores como arquivos.
  Quando a pasta selecionada tem arquivos na raiz, o hen-Nave agora envia os
  arquivos reais em ordem, com um arquivo da raiz primeiro para manter a pasta
  selecionada como base e preservar os caminhos relativos. Pastas sem arquivos na
  raiz usam o fluxo padrão do QtWebEngine. O LOG_GERAL registra a preparação de
  uma pasta com 125 arquivos; o usuário confirmou que também concluiu um upload.
  Isso valida o fluxo no Windows para o teste realizado.

[YTDLP-DNS] STATUS: HISTÓRICO; NÃO REPRODUZIDO NA VALIDAÇÃO ATUAL
Data descoberta: 2026-11-10
Descrição: O yt-dlp não conseguiu resolver o endereço de uma página da API do
  YouTube: `[youtube:tab] recommended: Unable to download API page:
  [Errno 11001] getaddrinfo failed`.
Como reproduzir: Tentar analisar ou baixar uma página do YouTube enquanto o
  Windows não consegue resolver o host do serviço.
Causa suspeita: Falha de DNS/rede, proxy ou firewall; a resolução do nome falha
  antes de o yt-dlp receber a resposta da API. O log sozinho não indica bug do
  navegador.
Solução / workaround: Confirmar internet e resolução DNS no Windows, revisar
  proxy/firewall e tentar novamente. Não desativar TLS nem ampliar permissões do
  navegador para contornar esse erro.
Verificação: A mensagem aparece somente no CRASH_NATIVO, cujo conteúdo está
  byte a byte idêntico às capturas anteriores. Não é uma falha nova da sessão
  validada. Se voltar a ocorrer em uma captura realmente nova, indica falha de
  resolução de DNS/rede, não um erro do fluxo normal de download já testado.

[PERFORMANCE-WINERROR-1455] STATUS: CORREÇÃO APLICADA; PAINEL VALIDADO NO WINDOWS
Data descoberta: 2026-11-10
Descrição: A atualização do painel de desempenho falhou durante a enumeração
  recursiva de processos Chromium com `OSError: [WinError 1455] O arquivo de
  paginação é muito pequeno para que esta operação seja concluída`.
Causa suspeita: O Windows estava sem memória comprometida/página de paginação
  suficiente para enumerar os processos. Isso não prova, por si só, um vazamento
  de memória do hen-Nave.
Impacto: O erro podia escapar do amostrador e interromper a atualização do QTimer
  em PerformanceMonitor.refresh.
Solução: O amostrador captura OSError junto com os erros do psutil e, se a
  enumeração dos filhos falhar, retorna a amostra disponível do processo raiz
  marcada como parcial. Isso mantém a interface ativa e permite novas amostras.
Verificação: Teste automatizado simula OSError 1455 e confirma a amostra parcial.
  O usuário confirmou que abriu e usou o painel de desempenho no Windows. O
  LOG_GERAL recente não registra um novo WinError 1455; o texto que permanece em
  CRASH_NATIVO é idêntico ao arquivo antigo. A medição parcial ainda é esperada
  quando o Windows não consegue enumerar os processos filhos.

Data descoberta: 2026-11-10

  Correlacionar horário, versão do executável e eventual fechamento real do app
  com um novo CRASH_NATIVO; não atribuir o evento aos erros do yt-dlp sem evidência.
Atualização 2026-11-10: O LOG_GERAL da sessão seguinte registra o evento em
  main.py:159, que corresponde a app.exec() no código atual, e continua registrando
  navegações até pelo menos 11:22:15. O aplicativo permaneceu ativo por mais de
  dois minutos após o aviso; não há evidência de encerramento nesse trecho. O novo
  CRASH_NATIVO é byte a byte idêntico ao anterior e não deve ser tratado como
  captura nova.
Nova sessão: O aviso voltou a aparecer em 11:24:38, e o LOG_GERAL continuou
  registrando navegações até 11:27:38. O usuário confirmou que, após o aviso,
  realizou download, upload e usou o painel de desempenho sem bloqueio. Não há
  impacto funcional observado nos testes relatados; a origem COM/Qt ainda não foi
  identificada. O filtro que ignorava a exceção foi removido para não mascarar
  falhas reais.
